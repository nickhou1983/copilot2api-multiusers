Github Device Flow

自动化登录方案

Automated Device Flow Login

由一个专用容器完成 GitHub 登录、填入 User Code 并点击授权。 既有轮询与凭证落盘逻辑一行未改，自动化只承接人工点击那一步； 任何失败都回退到原有手动流程，并附上浏览器截图。

01  ·  方案架构 04 / 12
Agent

这个容器里面是什么

Inside the login-agent container
Mandate

一只代替人点鼠标的手。容器只负责在无头浏览器里走完 GitHub 的设备授权页， 结果由 GitHub 直接回到代理的轮询里——agent 全程看不到令牌。

不接触 access token 不读写凭证目录 不感知账户配置 不对宿主暴露端口
server.js

接口与排队

只有两个端点：GET /health（附带排队深度）与 POST /login。共享密钥校验、64 KB 体积上限，请求进入互斥队列串行执行。

172 行 · node:http · 零 Web 框架
github.js

浏览器编排

按 launch → login → device_code → authorize 推进，并始终记录停在哪一步。会话复用持久化 profile，失败时立刻截图。

303 行 · Playwright · 唯一触网模块
selectors.js

页面定位

8 组 DOM 选择器，每组都是候选列表而非单一写死值。GitHub 一旦改版，只需要改这一个文件。

96 行 · 全部选择器的单一出处
codes.js

纯逻辑

User Code 规范化（兼容单框与逐字符两种页面）、七类失败判定、请求体校验。不依赖 Playwright，可离线单测。

192 行 · 19 个用例 · 不需要浏览器
基础镜像 playwright:v1.62.1-noble · 第三方依赖仅 1 个 · 以非 root 用户 pwuser 运行 唯一持久化的是 /data 里的浏览器 profile
02  ·  登录流程 05 / 12
Sequence

点一次按钮之后发生的六件事

From one click to credentials.json
01

发起设备流

admin 提交 {"auto":true}，后端照常调用 StartDeviceFlow()，拿到 user_code 与验证链接，轮询 goroutine 立即启动。

02

取出账户凭证

从 github_logins.json 读出该账户的 GitHub 用户名与密码。没有配置凭证的账户不会出现自动按钮。

03

调用 login-agent

另起 goroutine 走内网 HTTP，带 X-Agent-Token。agent 用互斥队列串行处理，避免多个 Chromium 同时占内存。

04

浏览器完成授权

登录 → 打开设备页 → 填码 → 等 Authorize 按钮从 disabled 解禁 → 点击。全程无头 Chromium。

05

轮询自然收敛

授权成功的一瞬间，原本就在跑的 CompleteDeviceFlow() 拿到 access token —— 这一段代码没有任何改动。

06

凭证落盘

令牌写入 <token_dir>/<id>/credentials.json，账户状态转为 authenticated，UI 自动刷新。

02  ·  登录流程 06 / 12
Admin UI

管理界面怎么用

Add accounts once, authenticate in one click
A

添加账户时一并填写 GitHub 凭证

新增账户表单多了 GitHub 用户名与密码两个字段，都可留空、之后再补。已有账户可通过表格里的 Login 按钮随时设置或清除。

B

Auto authenticate 按钮

仅当 agent 已启用、该账户已配置凭证且尚未认证时出现。原来的 Authenticate 按钮保留不变，两条路径并存。

C

进度与失败证据

对话框实时显示 running → succeeded / failed；失败时给出错误分类、浏览器截图，并继续展示 User Code 与链接供人工接管。

状态机 / Auto state
未配置 agent按钮不渲染
idle尚未发起
running浏览器执行中
succeeded已点击授权
failed回退手动

无论自动化成败，轮询 goroutine 都不会被中断—— 管理员随时可以自己完成授权，状态照样会翻成 authenticated。

03  ·  安全模型 07 / 12
Security

明文密码的五道约束

Where the credentials live and who can reach them
面 / Surface 措施 为什么
磁盘 独立文件 github_logins.json，权限 0600，临时文件 + rename 原子替换，不进 accounts.json。 与业务配置隔离，误备份 / 误提交的面更小。
HTTP 响应 对外只暴露 username 与 has_password 两个字段。 admin API 任何路径都取不回密码原文。
日志 密码不参与任何日志格式化；启动时只打印 agent URL，不打印 token。 实测全量日志中密码出现 0 次。
网络 login-agent 在 compose 里没有 ports 段，只在内网可达，调用需带 X-Agent-Token。 持有明文凭证的进程绝不能被宿主或公网触达。
Admin 入口 COPILOT2API_ADMIN_TOKEN 在 compose 中被标记为必填，缺失直接启动失败。 否则任何能打开 admin 的人都能用他人凭证发起登录。

Failure

失败分类与回退

Every failure returns a class, a message and a screenshot
error_class 含义
invalid_credentials用户名或密码不正确。
two_factor_required账户开启了两步验证，本方案不支持。
device_verificationGitHub 要求邮箱设备验证码（陌生 IP 常见）。
captcha触发了人机校验。
code_rejectedUser Code 被拒绝或已过期。
timeout超出 agent 超时时间（compose 默认 240 秒）。
unknown页面结构不匹配任何已知形态，截图是主要线索。
回退 / Fallback
✓User Code 与链接 继续显示
✓轮询 goroutine 不中断
✓失败截图 可在 UI 直接查看
✓手动授权后 状态照常翻转

分类判断刻意把设备验证放在两步验证之前—— 设备页面里同样含有 “authentication code” 字样，顺序错了就会误报。

04  ·  部署与验证 11 / 12
Limits

已知边界

What this does not solve
L1

不支持两步验证

开启 2FA 的账户会返回 two_factor_required 并停在那里。这是设计取舍，不是缺陷。

缓解：此类账户走原有手动流程。

L2

陌生 IP 的邮箱验证码

即使没开 2FA，GitHub 仍可能在新设备登录时要求邮箱验证码。

缓解：/data 持久化 profile 复用 cookie，首次通过之后基本不再触发。

L3

GitHub 页面改版

登录页与设备授权页的 DOM 变化会让选择器失效，这是所有浏览器自动化的共同风险。

缓解：选择器集中在 selectors.js，带 fallback，失败必附截图。

L4

登录请求串行执行

agent 用互斥队列逐个处理，避免多个 Chromium 同时驻留内存。批量账户是排队而非并发。

缓解：单次授权通常几十秒，批量场景预留时间即可。

关闭方式：不设置 COPILOT2API_LOGIN_AGENT_URL 即可，全部新功能静默下线 accounts.json 结构未变，老配置无需迁移
